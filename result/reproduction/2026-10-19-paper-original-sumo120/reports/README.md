# 山下論文 原本実装再現（SUMO 1.20.0）

## 再現境界

- Google Driveと保全原本は読み取り専用とする。
- 実験コードは `sumo-mcs-11/` の隔離コピーだけを変更・実行する。
- 原本ZIP: `ITS2602yamashi.zip`
- SHA-256: `2e499688c1d9298a796f77f8368e1eb23168407a29c4e1164f0f3f316027bde4`
- SUMO、TraCI、sumolib: 1.20.0
- Python: 3.10.20（原本に残る`cpython-310`生成物に合わせた）
- NumPy: 2.2.6（原本に版指定はない。結果作成時期の2025年12月〜2026年1月にPython 3.10が利用できる最新安定版だった2.2.6で固定）
- シミュレーション時間: 600秒
- ステップ長: 0.1秒

## 原本からの実行互換・計測非依存変更

1. Python 3.14で削除された未使用の`distutils.spawn` importを3ランナーから削除。
   正式実験はPython 3.10で行うが、削除対象は未使用であり計算には影響しない。
2. `MCS_QUIET=1`でデバッグ表示を抑制。計算・CSV出力は変更しない。
3. FCD XML出力を隔離コピーのSUMO設定から外す。走行状態・乱数・集計式は変更しない。
4. `MCS_RESULT_CSV`で各seedの結果ファイルを分離し、並列書込みの衝突を防止。
5. 原本が実験ごとにコメント切替していた車種選択を`MCS_BUS_MODE`で切り替える。
   `car`は全車Car、`random25`は原本どおり各車を`[Bus, Car, Car, Car]`から抽選する。
6. `MCS_DIAGNOSTIC_STOP_TIME`は実行環境比較専用。正式実験では未指定で600秒まで実行する。

保全原本との差分は`original-to-run-code.diff`へ固定した。キャッシュ、Git内部データ、
既存統計、実行ログ・結果を除く差分は223行・12,255 bytesで、上記の出力分離、
表示抑制、未使用import削除、FCD出力停止、車種切替、診断停止フックに限定される。

## 車両モデルと論文・原本実装の不一致

論文Table 5.1は全評価共通で次の車両性能を指定している。

| 種別 | `maxSpeed/accel/decel` |
| --- | --- |
| CAVcar | 13.89 / 3.0 / -5.0 |
| CAVbus | 11.11 / 1.0 / -3.0 |

一方、引き継ぎ原本の評価コードは場面ごとに異なる。

| 場面 | Car `maxSpeed/accel/decel` | Bus `maxSpeed/accel/decel` | 論文一致 |
| --- | --- | --- | --- |
| T字路 | 13.89 / 3.0 / -5.0 | 11.11 / 1.5 / -3.0 | Bus accel不一致 |
| 十字路 | 13.89 / 3.0 / -5.0 | 11.11 / 1.0 / -3.0 | 一致 |
| 合流 | 13.89 / 3.0 / -5.0 | 11.11 / 1.5 / -3.0 | Bus accel不一致 |

この矛盾を数値合わせで隠さず、次の2層で検証する。

1. このディレクトリでは同梱原本コードの値を保ち、原本実装再現を行う。
2. 原本実装の25ケース完了後、別の隔離コピー`sumo-mcs-11-paper-model/`で
   Busのクラス定数と経路計画器をTable 5.1の`11.11 / 1.0 / -3.0`へ合わせ、
   Busを含むT Eval.3、Four Eval.5、Merge Eval.7を正しいseed集合で再実行する。
   Busを含まないEval.4/Eval.6は原本実装版を再利用できる。

追加監査により、原本のBusクラス定数だけでは車両性能が完全には反映されないことを確認した。
実際の軌道候補の速度・加速度・減速度検査と緊急停止は、インポートしたFrenet経路計画器の
`MAX_SPEED`、`MAX_ACCEL`、`MAX_DECEL`を使う。ところが原本では次の状態だった。

- T字路・十字路のBusクラスはCarと共通の計画器（`13.89 / 3.0 / -5.0`）を使用する。
- 合流用の`frenet_merge_bus.py`は存在するが、Busクラスは`frenet_merge_car.py`をインポートする。
- 未使用の合流Bus計画器自体も加速度が`1.5`で、論文値`1.0`と異なる。

したがって論文条件版では、T字路・十字路に原本計画器から分離したBus版を置き、合流は
原本同梱のBus版へ接続する。3つのBus計画器はいずれも`11.11 / 1.0 / -3.0`とする。
これは数値合わせではなく、論文Table 5.1を軌道生成・軌道検査・緊急停止へ一貫して適用するための変更である。

原本ランナーはBusもSUMOへ`typeID="CAV_0"`で追加し、SUMO側vTypeは
`20.0 / 3.0 / 5.0`のままである。一方、各CAVは`setSpeedMode(0b100000)`と`setSpeed`で
計画軌道の速度を直接与えるため、論文条件版でもSUMO側に新規vTypeは追加せず、
制御コードと経路計画器の制約を車種別にする。

論文条件版の隔離コピーと`run_paper_model_py310.sh`は準備済みである。ランナーは
原本実装版の`queue-status.log`に`ALL_DONE`が記録されるまで待機し、その間は追加の
シミュレーションを起動しない。開始後はEval.3/Eval.5/Eval.7の各5 seed、計15ケースを実行し、
Busクラス3ファイルとBus計画器3ファイルのSHA-256も結果ディレクトリへ保存する。
原本実装版から論文条件版への差分は`paper-vehicle-model.diff`へ固定する。
`validate_paper_vehicle_model.py`は3場面のBusクラス定数、import先、計画器制約をASTで検査し、
検証結果を`paper-vehicle-model-validation.json`へ保存する。2026-10-19時点で全21チェックが通過した。
`validate_vehicle_model_behavior.py`は初速10 m/sの緊急停止軌道を3場面で実行し、
Carが2.0秒・10.0 m、論文条件Busが3.4秒・16.66 mで停止することを確認する。
結果は`paper-vehicle-model-behavior-validation.json`に保存し、全チェックが通過した。

Google Driveの接続先 `sy921@keio.jp` で2026-10-19に読み取り専用のフォルダ一覧を再取得し、
5つの評価CSVのID・サイズ・更新日時を
`drive-result-metadata-2026-10-19.json` に保存した。Drive上のファイルや権限は変更していない。
Eval.3、Eval.5、Eval.6、Eval.7はDriveミラーと引き継ぎZIP内コピーのSHA-256も一致した。
Eval.4の`acceptance_four_4.3.2_all300.csv`はZIPに同名ファイルがないため、Drive取得物を正本とする。

ZIP内の更新時刻を比較すると、保存CSVより同梱コードの更新日時が後の評価がある。
この日時差は結果生成版を特定するうえでの不足を示すが、計算ロジックが変わったことや残差の原因を直接証明しない。

Google Driveの「コード」フォルダにはZIPが1個だけで旧リビジョンもなく、同名ソースの別ファイルも
見つからなかった。さらに同梱Gitの`.gitignore`は2行目で`*`を指定しており、これらの評価コードは
すべてGit管理対象外なので、コミット履歴から結果生成時点へ戻すこともできない。したがって、
Eval.3〜6で差が残る場合は、数値合わせで補正せず
「結果生成時のソース版が特定できていない」を検証上の制約として扱う。
ソース版差が残差を引き起こしたかは未確定であり、依存環境等の候補と区別して検証する。

## Mac未使用時だけの実行制御

2026-10-20のユーザー指示で、この制限は解除した。現在はコントローラーを終了し、
残りの論文モデル15件を連続実行する。以下は以前の制御の記録であり、現在は適用しない。
待機判定がawk自身を数える不具合を修正し、Python実行ファイルと対象スクリプトの
引数フィールドを照合するよう変更した。未開始の待機シェルだけを置き換え、原本25件の結果は保持した。

ユーザー作業中の負荷を避けるため、長時間バッチは`idle_run_controller.py`で制御する。
固定時刻は使用しない。macOSの`IOHIDSystem.HIDIdleTime`を15秒間隔で読み、次の条件で
原本・論文モデル両方の既存プロセス木へ`SIGSTOP`/`SIGCONT`を送る。

- キーボード・ポインタ操作が10分以上ない場合だけ、停止位置から再開する。
- 明示的な再開指示時は`--resume-now`で待機を省略できる。以後の新しい操作を検知すると停止し、通常の10分待機へ戻る。
- 操作が戻ってidle時間が2分未満になると、15秒以内に再停止する。
- 再開中だけ`caffeinate -i`でシステムのidle sleepを抑止する。画面スリープは許可する。
- 停止中は`caffeinate`も終了し、通常のMacスリープ設定へ戻す。
- プロセスを終了・再起動せず、TraCI/Python/SUMOの組をまとめて停止・再開する。

状態遷移は`idle-run-controller.log`へ記録する。全40件の完了後は
`finalize_when_done.sh`が構造・挙動検証、CSV集合、ログ異常、残存プロセス、
原本ZIPハッシュを監査し、最終分析JSON・Markdownを生成する。

## 入力乱数の版差監査

`audit_random_inputs.py`で各評価の原本runnerと同じ順序で、出発時刻、経路、
Bus/Car抽選を再生成した。Python 3.9.6と3.10.20の全25 seedで入力系列の
SHA-256は一致した。さらに`validate_random_inputs.py`で、原本CSVに保存された
経路別Bus/Car生成台数と25/25 seedで一致することを確認した。

したがって、少なくともPython 3.9から3.10への標準`random`実装差は数値残差の
原因から除外できる。NumPy乱数は車両投入に使われていない。証拠は
`random-input-version-comparison.json`と`random-input-reference-validation.json`へ保存する。
