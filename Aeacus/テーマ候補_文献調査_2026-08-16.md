# Aeacus周辺の通信性能研究：文献調査と卒論テーマ候補

調査日: 2026-08-16

## 結論

最有力は、次のテーマである。

> **QUIC接続結果に基づくDNSキャッシュ再検証方策の設計と評価**

DNSキャッシュ済みIPへのQUIC接続がタイムアウトしたとき、単純にそのIPを古いとみなして消すのではなく、同一IPへの再接続と最新DNS応答を使って、`古いIP`・`一時障害`・`原因不明の継続障害`を区別する。区別結果に応じて、キャッシュを維持・無効化・短い再検証へ分ける方策を比較する。

これはAeacusの問題設定を保ちながら、5GC・UE・UPFの実機改修を前提にしない。現在のDocker実験を拡張し、遅延、誤ったキャッシュ無効化、DNS問い合わせ量を同一条件で測れる。新規性を過大に主張するのではなく、**「タイムアウトをDNS不整合の証拠として扱う際、どの確認をすれば誤った無効化を減らせるか」**を実装と実験で答える卒論にする。

## 研究課題

AeacusはQUICハンドシェイク失敗をDNSキャッシュ不整合の手掛かりにする。一方、タイムアウトだけでは、古いIP、瞬間的なパケット損失、宛先側の障害を区別できない。

### Aeacusとの差と、この案だけでは足りない点

Aeacusの論文上の状態機械では、**有効TTL内のキャッシュ**に対するハンドシェイク失敗を server-triggered cache invalidation として扱う。すなわち、該当キャッシュを削除し、クライアントの再試行を更新済みレコードへ向ける。一方、**期限切れキャッシュ**では、旧IPへInitialを直ちに転送しながらDNS再解決を並行させ、応答がなければ更新先へ転送する。したがって「失敗後にDNSを引き直す」ことはAeacusの中心機能であり、新規ではない。

このため、同一IPへの1回の再接続とDNS再問い合わせを加えただけの案は、**卒論の小さな安全化パッチとしては成立しても、新規性の主張としては弱い**。採用するなら、少なくとも「一回の追加試行」という手順ではなく、次のような検証可能な意思決定問題にする必要がある。

> **接続失敗の観測列から、キャッシュを維持・無効化・隔離のどれにするかを、回復遅延と誤無効化のコストを用いて選ぶ方策は、Aeacus型の即時無効化より有利か。**

具体的には、初回失敗の種類（即時の `CONNECTION_CLOSE` / 無応答タイムアウト）、同一IPプローブ、強制DNS再解決、更新IPへの接続結果、直近の失敗回数を観測として扱う。キャッシュ状態を `active`、`suspect`、`invalid`、`network/server failure` に分け、無応答だけでは直ちに削除せず短い再検証期間へ入れる。比較はAeacus型即時無効化、固定回数リトライ、提案するコスト考慮方策とする。

この拡張でも、実ネットワークの障害確率を推定する研究にはならない。制御環境で、誤無効化率、古いIPの見逃し率、回復完了時間、追加DNS/QUIC試行数のトレードオフを示す研究になる。ここまで設計・比較できなければ、DNS再検証案は順位を下げ、情報鮮度スケジューリングを主題にする。

そのため、次の問いを立てる。

> **Q. キャッシュ済みIPへのQUIC初回接続が失敗したとき、どの追加確認とキャッシュ方策が、接続開始遅延を抑えつつ誤ったキャッシュ無効化を最も減らすか。**

### 提案方策（卒論で実装・評価する範囲）

初回接続が成功したら、従来どおりキャッシュを利用する。タイムアウト時だけ、以下を並行して行う。

1. 同じIPへの新しいQUIC接続を一度だけ試す。
2. DNSへ最新Aレコードを問い合わせる。
3. DNS応答が変わった場合だけ、新IPへの接続も試す。
4. 結果に応じて、キャッシュを維持・無効化・短い再検証対象に分ける。

`DNSが変わった`だけでは旧IPが使えないとは限らないため、旧IPが再接続で成功したケースは無効化しない。この点が、失敗=古いIPとみなす単純方策との差になる。

### 比較する方策

| 方策 | タイムアウト時の動作 | 役割 |
| --- | --- | --- |
| TTL厳守 | TTLまで古い値を使用 | 通常DNS寄りの基準 |
| 即時無効化 | 初回タイムアウトでキャッシュを削除しDNS再問い合わせ | Aeacusの失敗利用を単純化した基準 |
| DNS変化のみ | DNS応答が変われば旧値を削除 | 「DNS変更=古いIP」の危険性を示す基準 |
| 提案方策 | 同一IP再接続・DNS・必要時の新IP接続を用いて分類 | 評価対象 |

### 測定指標

- 接続開始完了までの時間（平均だけでなく p50 / p95）
- 接続成功率
- 旧IPがまだ使えるのに削除した割合（誤無効化率）
- 古いIPを保持し続けた割合（見逃し率）
- 1接続あたりの追加QUIC試行数とDNS問い合わせ数

### 最小シナリオ

| シナリオ | 旧IP | 最新DNS | 正しい判断 |
| --- | --- | --- | --- |
| 正常 | 接続可能 | 旧IP | 追加確認なし |
| 一時損失 | 後の再接続では可能 | 旧IP | キャッシュ維持 |
| 実際のIP移動 | 接続不能 | 新IP | 旧IPを無効化 |
| 継続障害 | 接続不能 | 旧IP | DNS不整合と断定しない |
| DNS変更だが旧IPも可能 | 再接続で可能 | 新IP | 旧IPを即時無効化しない |

遅延、損失率、DNS応答遅延、障害継続時間、IP切替時刻を変化させ、各条件を繰り返す。実験で扱うのは制御した障害であり、実ネットワークでの障害原因の割合を示す研究ではない。

## 既存環境から出発できること

`Aeacus/aeacus_lab/experiment.py` には、実際のQUICハンドシェイク、UDP破棄、DNS応答、qlog出力がある。現在の5シナリオを各20回実行した既存結果は、期待分類と全試行が一致している。

ただし、現状は**分類ロジックの制御実験**までである。比較方策ごとの接続開始遅延、誤無効化率、DNS問い合わせ量を集計していない。また、5GC、UE Initialの転送、UPF/NAT、実運用の障害分布を再現していない。これらを再現済みとは呼ばない。

ローカルの `python3` には `aioquic` が入っていないため、ユニットテストはDocker環境または依存関係を入れた仮想環境で実行する必要がある。

## 着手時の完了条件

テーマをAに決めた場合の最初の完了条件は、次の4つである。

1. 上表の4方策を同じ実験ドライバから選択可能にする。
2. 5シナリオに遅延・損失・DNS遅延のパラメータを加える。
3. 各条件で十分な反復を行い、CSV/JSONから p50・p95・成功率・誤無効化率・DNS問い合わせ量を出す。
4. 「どの条件では提案方策が有利で、どの条件では追加確認の分だけ不利か」を図表で示す。

この範囲が終わって初めて、実験結果に基づいて「有効」と言える。5GC全体を再現した、実ネットワークの原因を識別できた、一般の商用サイトにそのまま適用できる、とは主張しない。

## 拡張サーベイ（2026-08-16 追記）

「QUICを使う」こと自体は性能改善の答えではない。実運用のQUIC性能は、接続開始、経路変化、無線区間の輻輳、データ種別、実装・設定に強く依存する。本サーベイでは、各系統を次の4条件で評価した。

1. 性能上の問題が明確か。
2. 比較対象を用意できるか。
3. 現在のDocker / Aeacusコードを再利用できるか。
4. 5GC実機・複数の実回線・大規模なプロトコル改変なしに終えられるか。

### 1. 接続開始・DNS系

Aeacusは、DNS応答を待つ経路とQUIC Initialを連携させ、さらに接続成否をキャッシュ制御へ用いる。QuicSocksも、DNSを待たずにプロキシへInitialを送り、解決後に転送するという近い構成である。DoQ研究は、暗号化DNSでも接続再利用の有無やページの複雑さで効果が変わることを示す。

この系統の長所は、問題、比較対象、測定指標が素直なこと。現在の簡易実験もこの系統にあり、最も確実に卒論へ育てられる。逆に、5GCへ置いたAeacusと同じ性能を再現する研究ではなく、制御されたDocker実験で**キャッシュ制御の意思決定**を比較する研究として限定する必要がある。

### 2. モバイル切替・接続移動系

mQUICは、送信エラーまたはタイマでハンドオーバーを検知し、新IPでパス検証と移動を実行する。商用5GとWi-Fiの試験で、新接続を作る通常方式より性能上の利点を示した。これは「通信性能向上」の見た目が最も分かりやすい。

ただしQUIC標準では、移動はハンドシェイク完了後に限られ、パス検証に少なくとも1 RTTかかる。実際に使えるかは端点実装にも依存する。現在のAeacus公式 `quiche` は `NEW_CONNECTION_ID` / `RETIRE_CONNECTION_ID` の処理に接続移動未実装の注記があり、ここを卒論の主目的にすると、評価前に実装基盤を直す時間が大きい。

### 3. エッジ中継・QUICトンネル系

暗号化QUICでは、従来のTCP Performance Enhancing Proxyのように途中でヘッダを見て分割することはできない。MASQUEはクライアント合意のトンネルを使ってUDPを中継する標準であり、TECCはトンネル端点で無線側に近いフィードバックを使う研究である。TECCは、損失が小さいとトンネルの追加コストで不利になり得る一方、損失や帯域変動が大きいモバイルトレースではtail FCTを改善した。

研究テーマにするなら、次のように絞る必要がある。

> **QUICトンネルを使うべき回線状態の閾値は何か**

常時トンネル、常時直結、損失/RTT推定に基づく切替を比較する案である。ただしMASQUE対応のクライアント・プロキシ・サーバを準備するため、今は候補Bに留める。

### 4. 5G上の輻輳制御系

Haileらは5Gトレースのエミュレーションと実験で、CUBIC、BBR、Copa、RBBRをQUIC上で比較した。輻輳制御器によって、bufferbloat、遅延、throughputのどれを犠牲にするかが変わる。Production QUICの測定研究も、QUICの性能はプロトコル名よりサーバ側CCAや実装設定に左右されると指摘している。

これは本格的な性能研究だが、CCAを変更しても、帯域変動を妥当に与えられなければ「自作条件だけで速い」結果になりやすい。まずは公開トレースまたは十分に説明できる `tc netem` 条件を使える場合だけ候補にする。今の段階では、DNSキャッシュ研究の条件設計（遅延・損失・帯域を独立に掃引する）へ知見を借りるのがよい。

### 5. ストリーム優先・期限系

HTTP Priorities (RFC 9218) は、HTTP/3で応答の緊急度と増分送信の性質を伝える。QUIC実装がアプリケーション指定の優先度を扱えるなら、新規データと再送のどちらを先に送るかも優先度を考慮できるが、具体的なスケジューリングは標準が決めていない。ここに小さな研究余地がある。

現在の `quiche` には `stream_priority(stream_id, urgency, incremental)` があり、低い urgency のストリームを先に送る実装テストもある。したがって次の候補は、実装基盤がある。

> **混雑時のHTTP/3ストリーム優先制御が制御応答のtail latencyに与える影響**

例えば、状態取得・制御応答（小・高優先）とログ/ファイル送信（大・低優先）を同一QUIC接続に流す。FIFO、固定優先、待ち時間に応じた優先度更新を比較し、制御応答p95と背景転送の劣化を測る。ネットワークを狭帯域・損失・遅延で掃引でき、バックエンド的な実装も多い。

課題は、HTTP/3の `PRIORITY_UPDATE` を最後まで扱うか、QUICライブラリのAPIでアプリ内優先度を直接設定するかを最初に決めること。後者なら卒論範囲に収まるが、「標準フレーム全実装」までは主張しない。

### 6. DATAGRAM・情報鮮度系

QUIC STREAMは順序と再送を保証する。一方、QUIC DATAGRAMは古い状態を再送して到着させる必要がない用途に向く。時刻と連番を付け、古いデータを受信側で捨てることで、「到着したパケット数」ではなく最新状態がどれだけ早く届くかを評価できる。Age of Information (AoI) は、受信済みの最新値が生成されてからどれほど古いかを表す指標である。

この方向には、ChiariottiらのQUIC-ESTがある。相関した複数のデータ流について、アプリケーションが持つValue of Information (VoI) を最大化するスケジューラをQUIC上へ載せた研究である。題材は自動運転と触覚通信だが、卒論で同じ題材を再現する必要はない。「最新の監視状態は価値が高く、古い状態は価値が下がる」という小さいモデルに置き換えられる。AoIだけでなく、最新状態を優先する理由をVoIとして説明できる点が強い。

現在の `aioquic` は `send_datagram_frame`、`max_datagram_frame_size`、HTTP/3 Datagramの実装とテストを含む。従って次の候補も現実的である。

> **帯域変動・損失下での最新状態配信におけるQUIC STREAM / DATAGRAM選択方策**

比較は、常にSTREAM、常にDATAGRAM、更新頻度や直近AoIに応じて送信方式を切り替える方策とする。さらに、複数の状態流があるときはFIFO、固定優先、AoI/VoI優先を比べられる。指標はAoI、期限超過率、最新状態到達遅延、欠落率、制御メッセージ成功率である。V2Xに戻らず、監視値・ゲーム状態・共同編集のような一般的な「頻繁に変わる状態」を題材にできる。

DATAGRAMは信頼配送ではないため、決済・DB更新・最終的に必ず届くべきコマンドには使えない。この制約を明示し、`制御コマンドはSTREAM、観測状態はDATAGRAM` のように分けて評価する。

### 7. マルチパス系

2026年3月時点のIETF Multipath QUIC草案は複数経路の管理を規定するが、アドレス発見とスケジューリングはアプリケーション側に委ねている。STORMは不安定なWi-Fi/5Gで、信頼データと非信頼データを区別するスケジューリングを提案している。

「どの経路へどのデータを流すか」は大きな研究テーマだが、複数ネットワーク、MPQUIC対応実装、端末の無線情報を要する。現時点では読む対象にはするが、卒論の最初のテーマには採用しない。

### 最も取り組みやすい案: 情報鮮度を意識したQUIC優先スケジューリング

研究題目のたたき台は、次のとおり。

> **帯域制約下におけるQUIC複数状態ストリームの情報鮮度を考慮した優先スケジューリングの実装と評価**

送るものは、たとえば温度・位置・在庫のような3種類の「頻繁に更新される状態」でよい。実車やセンサ実機は不要で、一定周期にタイムスタンプ付き値を生成する小さいクライアントとサーバを作る。

- FIFO: 発生順に送る。
- 固定優先: 重要な状態だけ常に先に送る。
- 提案: 最後に届いた値が古い状態を優先する（AoI優先）。

測るのは、受信側のAoI、各状態のp95到達遅延、期限超過率、背景ストリームへの影響である。QoSを「何Mbps出たか」だけでなく「最新の状態が間に合ったか」で評価できる。`quiche` にはストリーム優先度APIとテストがすでにあるため、QUIC自体のスケジューラを一から書く必要はない。相関行列、複数NIC、ネットワークスライシングまで入れないことが、この案を卒論サイズに保つ条件である。

### 次点: DoQの接続再利用

題目のたたき台は、次のとおり。

> **問い合わせ間隔を考慮したDNS over QUIC接続再利用方策の性能評価**

DoQの先行研究は、継続接続・過去セッションの再開・0-RTTの評価を今後の課題としている。ここでは「問い合わせ頻度が高いときに接続を保持する価値があるか」「idle後にいつ閉じると無駄な維持コストを避けられるか」を実装して比較する。

この案は小さく始めやすいが、接続再利用が効くのは複数問い合わせが短時間に続く場合という、かなり予想しやすい結果になりやすい。提案方策を問い合わせ間隔・RTT・損失へ適応させるまで進められるかが、卒論としての面白さを左右する。

### Aeacus非5G化を最初に選ばない理由

Aeacus自身は非5Gネットワークへの適用を今後の課題として明記している。ただしこれは「5Gを外せば簡単」ではない。論文が前提とする、ゲートウェイでのルーティング、LDNS、クライアント側の変更を、別の形で用意する必要がある。現在の環境で確認済みなのはHTTP/3と従来型DNSの部品であり、Aeacus全体のデータパスではない。

したがって、Aeacusを主題に残したいなら先に順位AのDNSキャッシュ制御を選ぶ。通信性能一般として最もとっつきやすいものを選ぶなら、順位Aの情報鮮度スケジューリングを選ぶ。

## 卒論として実際に進めるフロー（推奨案）

ここでは、今後の展望・実装可能性・評価の明快さを合わせて、次を最終候補として進める。

> **帯域制約下でのQUIC状態ストリームに対するAoIベース送信選択の実装と評価**

この題目で問うのは、単に「QUICの優先度が使えるか」ではない。

> **Q. 同一QUIC接続で頻繁に更新される複数の状態と背景データを送るとき、古い未送信状態をまとめ、受信側で古くなった状態を優先して送ると、FIFO・固定優先と比べて情報鮮度を改善できるか。背景転送にはどの程度の代償があるか。**

QUIC-ESTは多ストリーム相関データの一般的な送信枠組みを課題として残し、主にシミュレーションで評価した。一方、HTTP Prioritiesは優先度の表現を定めるが、具体的なスケジューリング手法を定めない。従って、一般的な監視状態に題材を縮小し、実QUIC実装上で比較する余地がある。ただし、QUIC-ESTの自動運転・触覚通信を再現した、VoI最適解を得た、とは主張しない。

### 研究の境界を先に固定する

| 入れる | 入れない |
| --- | --- |
| 1クライアント・1サーバ・1本のQUIC接続 | 5GC、実車、実センサ、複数NIC |
| 3種類の合成状態（例: 温度、位置、在庫）と背景ファイル転送 | MPQUIC、ネットワークスライシング、相関行列の最適化 |
| FIFO、固定優先、AoI優先の比較 | QUIC輻輳制御器そのものの改変 |
| 制御した遅延・損失・帯域制約 | 実モバイル網での一般的な性能主張 |
| AoI、到達遅延、期限超過、背景転送完了時間 | 「常に最速」「全用途に有効」という主張 |

### 実装の要点

AoI（Age of Information）は、受信側が最後に受け取った値の生成時刻を `t_gen` としたときの `現在時刻 - t_gen` である。値の発生から到達までの1回の遅延とは異なり、「受信側の情報が今どれほど古いか」を連続的に測れる。

各状態には生成時刻と連番を付ける。送信待ちの間に同じ状態の新しい値が発生したら、まだQUICへ投入していない古い値を新しい値で置き換える（**coalescing**）。すでにQUICへ投入したバイトを取り消すことはしない。送信ループは各状態について最新の未送信値だけを持ち、方策に従って次に投入する状態を選ぶ。

| 方策 | 送信選択 | 意味 |
| --- | --- | --- |
| FIFO | 発生順 | 比較の基準 |
| 固定優先 | あらかじめ決めた重要度順 | 「重要な状態だけ優遇」の基準 |
| AoI優先（提案） | `重み × 現在AoI` が最大の状態 | 長く更新されていない状態を救う |

初版は、信頼配送が必要な状態をQUIC STREAMで送る。各状態を別ストリームにして、`quiche` の `stream_priority(stream_id, urgency, incremental)` を送信前に設定する。背景の大きなデータは低優先の別ストリームに置く。QUIC DATAGRAMは、第2段階で「古い状態は再送不要」という仮説まで調べたくなった場合だけ加える。STREAM と DATAGRAM を同時に主題にすると、送信方式と選択方策の効果を分離できなくなるため、最初から両方を評価しない。

### フェーズ0: 研究質問を1枚に固定する（1日）

1. QUIC-EST、RFC 9218のサーバスケジューリング節、`quiche` の優先度APIの3点を読む。
2. 上の研究質問、3方策、4指標、範囲外をA4一枚に書く。
3. 「AoI優先はFIFOより各条件で必ず良い」という仮説にはしない。**帯域競合がある条件で、低頻度または重みの高い状態のp95 AoIを下げられるか**を仮説にする。

ここで指導教員に確認すべき一点は、題材を「一般的な監視状態」としてよいかである。V2X・自動運転と呼ぶ必要はない。

### フェーズ1: 測れる最小系を作る（1〜2週間）

クライアントは3状態を異なる周期で生成する。例として、状態Aを100 ms、Bを300 ms、Cを1000 msごとに生成し、各メッセージへ `state_id`、`sequence`、`generated_at`、値を入れる。サーバは受信時刻と生成時刻をJSON Linesへ記録する。背景ストリームは十分に大きい連続データを送る。

完了条件は、次のすべてである。

1. 制限のないローカル条件で、各状態の連番・生成時刻・受信時刻が記録できる。
2. FIFOだけを実装し、AoIの時系列と平均・p95をオフライン集計できる。
3. 背景転送の開始・終了時刻、接続ID、実験条件、乱数seedを同じ試行記録に残せる。
4. 1試行をコマンド一つで再実行できる。

この段階では「性能向上」はまだ示さない。正しい計測系を作ったことだけを確認する。

### フェーズ2: 比較可能な負荷を作る（3〜5日）

現在の `Aeacus/compose.yml` はUDP破棄の実験用であり、帯域・遅延制御は未設定である。したがって、次の順で進める。

1. まずアプリケーション側のtoken bucketで送信可能量を制限し、背景データと状態更新を競合させる。これは再現可能な**アプリケーション層の負荷モデル**として明記する。
2. Dockerコンテナで `NET_ADMIN` と `tc netem` が動作することを別途確認できた場合だけ、遅延・損失・帯域をネットワーク側にも加える。確認できない環境では、無理に5Gエミュレーションと呼ばない。
3. 条件は最初は3個に絞る。例: (a) 制約なし、(b) 競合する狭帯域、(c) 狭帯域+固定損失。条件を増やすのは基準実験が安定してからにする。

### フェーズ3: 方策を一つずつ増やす（1〜2週間）

FIFOを凍結してから、同じ計測・同じ負荷生成のまま固定優先、AoI優先を追加する。方策以外を同時に変えない。

AoI優先の初版は、難しい学習器や予測器を使わない。送信時刻 `now` に各状態の受信側推定AoIを計算し、`score_i = weight_i × AoI_i` が最大の状態を選ぶだけでよい。サーバからの確認応答が必要なら、最新の受信連番だけを小さい確認メッセージで返す。最初は完全な推定が難しければ、クライアント側の「最後に送った生成時刻」を用いる近似を明記する。

同じ状態の未送信値をまとめるかどうかは、方策の効果と混ざる。次のどちらかを事前に決め、全方策に共通適用する。

- **基本案（推奨）**: coalescingを全方策に共通適用し、「選択順」の違いだけを比較する。
- 拡張案: FIFOのみcoalescingなしも追加し、古い更新を送ってしまうコストを補助的に示す。

### フェーズ4: 実験計画を固定して回す（1〜2週間）

各「方策 × 回線条件 × 状態更新パターン」を少なくとも30回繰り返し、方策の実行順を混ぜる。ネットワーク条件を変える前に、同じ条件で分布が安定するかを確認する。

最低限の表は次のとおり。

| 要因 | 最初の水準 | 目的 |
| --- | --- | --- |
| 方策 | FIFO / 固定優先 / AoI優先 | 提案の効果を分離する |
| 競合 | 背景なし / 背景あり | 優先制御が必要な条件を作る |
| 送信制限 | 余裕あり / 逼迫 | 効果が出る境界を調べる |
| 損失 | なし / 固定損失 | 再送と混雑下での頑健性を確認する |
| 状態周期 | 例: 100 / 300 / 1000 ms | 更新頻度の違いを作る |

主要指標は、状態ごとの時間平均AoIとp95 AoI、最新値のp95到達遅延、期限超過率、背景転送完了時間である。全状態を平均した値だけでなく、固定優先で不利になる低優先状態も必ず示す。性能が改善した方策が背景転送をどれほど遅らせたかを同じ図表に出す。

### フェーズ5: 結果の読み方を先に決める（3〜5日）

期待する結論は「AoI優先が常勝」ではない。

| 観測結果 | 言えること |
| --- | --- |
| 逼迫時だけAoI優先のp95 AoIが下がり、背景転送は少し遅くなる | 鮮度と背景性能のトレードオフを定量化できた |
| 余裕時は3方策がほぼ同じ | 優先制御が不要な条件を示せた |
| 固定優先は重要状態を改善するが、低優先状態のAoIを悪化させる | 動的選択を導入する理由を示せた |
| AoI優先が改善しない | 状態周期・負荷・実装上のキュー位置を確認し、適用条件または限界として報告する |

改善しない結果でも、測定系、比較、適用条件が明確なら卒論として失敗ではない。効果が出ないからといって、途中でMPQUICや5G実機へ範囲を広げない。

### フェーズ6: 論文の形へ戻す（並行して継続）
