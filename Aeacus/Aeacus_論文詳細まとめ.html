Aeacus: QUIC-Powered Low-Latency and Strong-Consistency Name Resolution in 5G

5Gコアに置くミドルウェアによって、DNSのTTLキャッシュが抱える「低遅延 vs. 更新整合性」のトレードオフを、QUIC接続開始の状態を手掛かりに緩和する研究。

Li et al.IEEE Transactions on Mobile Computing24(7), 5981–59952025DOI: 10.1109/TMC.2025.3539590

結論を先に

Aeacusは、UE（端末）からの通常のDNS問い合わせを先に完了させる代わりに、QUICの最初のハンドシェイク・パケットを5Gコア内のAeacus resolverへ送る。resolverはそこからSNIのドメイン名を取り出して名前解決し、同じパケットを実サーバへ転送する。そのため、DNSの応答を端末へ往復させる1 RTTを接続開始のクリティカルパスから外せる。

もう一つの核はキャッシュ制御である。 TTLが切れたレコードも、名前解決を並行して更新しながらまず使う。接続が成功すれば古いレコードでも実用上有効、失敗すればQUICの失敗を検知して即座にキャッシュを削除・再問い合わせする。つまりTTLの経過だけでなく、実際に接続できたかをキャッシュの妥当性判断へ取り込む。

論文の商用5Gネットワークとテストネットワークでの評価では、通常DNSに比べて接続開始遅延を8.9%〜71.8%削減したと報告している。追加の解析・転送に伴うオーバーヘッドは、最良のDNSキャッシュヒット条件との比較で約5.9%である。

DNS / TTL

DNSキャッシュ

ドメイン名からIPアドレスを引く。TTL（Time To Live）の間、LDNSはA/AAAAレコードを再利用する。長TTLはヒット率を上げて速い一方、サーバ移転・負荷分散でIPが変わった後も古いIPを返しやすい。

QUIC

接続IDとハンドシェイク

UDP上の暗号化されたトランスポート。TLSと一体化した接続開始、接続ID、0-RTT、アドレス移行を持つ。初期ハンドシェイクには接続先名（SNI）が含まれ、初期パケットは所定の鍵で中継者も復号可能である。

5GC

5Gコア

UEとインターネットの間のコア網。UPFはユーザプレーンの転送・ルーティング、EASDFはエッジサーバ発見に関わるLDNSを担う。Aeacusはこの中に置かれる。

用語の注意

本論文の「強一貫性」

分散システムの線形化可能性を証明する主張ではない。論文では、古いDNSキャッシュが接続失敗を起こすと、TTLを待たず数秒で検知・更新し、端末のリトライを最新レコードへ向けられる性質を指す。

問題設定：TTLだけでは両立しない

従来DNSでは、キャッシュの有効期限をどう設定するかが本質的なジレンマになる。長TTLなら名前解決の問い合わせが減り低遅延だが、IP変更を反映するまで遅い。短TTLなら更新は比較的速いが、キャッシュミスが増え、端末→LDNS→権威DNSという問い合わせの遅延を毎回負担する。

長いTTL短いTTLAeacusの狙い
名前解決遅延小さい ヒットしやすい大きい ミスしやすい期限切れでも接続可能なら暫定利用し、ヒット率を高める
IP更新への追従遅い 古いIPを保持速い接続失敗を観測した時点でTTLを待たず失効・更新する

著者らの商用5G測定（Alexa Top 500のうち測定対象）では、NSレコードの90%以上が1日超のTTLなのに対し、WebサーバのAレコードでは80%以上が10分未満だった。WebサービスはIP変更への追従を優先して短いAレコードTTLを使う傾向があり、キャッシュミスが接続開始遅延を増やす。

端末と5GC間のRTT RT_TRAN の中央値は名前解決に約20 msを加え、最適配置されたサーバへのRTTより最大21倍になり得た。99パーセンタイルでは RT_TRAN が122 msを超え、モバイルアクセス区間の往復が特に痛いことを示す。

何を変えるか：DNS往復をQUIC接続開始に重ねる

従来のDNS + QUIC
  1. UE → LDNS: DNS問い合わせ
  2. LDNS → UE: IPアドレス応答
  3. UE → サーバ: QUIC Initial
  4. サーバ → UE: ハンドシェイク応答

DNS応答が届くまで、QUICを開始できない。

→
Aeacus
  1. UE → Aeacus resolver: QUIC Initial
  2. resolver: SNIを抽出しDNS解決
  3. resolver → サーバ: 宛先IPを書換えてInitialを転送
  4. サーバ → UE: 応答（5GCが必要なNAT処理）

DNS応答をUEへ返す1往復をなくし、解決と転送を連結する。

preferred_address を利用

resolverはハンドシェイクを復号してSNIを得た後、LDNSへ問い合わせる。取得IPに宛先を書き換えて、受信したInitialをそのまま実サーバへ転送する。アプリケーションデータは接続開始後、resolverを経由せずUEとサーバの間で直接流れる設計である。

late binding（サーバアドレスへの切替）

最初のパケットの宛先はAeacus resolverだが、応答は実サーバから来る。このIP非対称性を放置すると、ファイアウォールやQUICクライアントが未知の送信元として破棄する。そこで5GCゲートウェイがNATと組み合わせて応答の送信元IPをresolverのIPに合わせる。UEは応答のQUIC transport parameter preferred_address にある実サーバIPを読み、ハンドシェイク完了時に実サーバへ移行する。この preferred_address はQUIC標準では任意だが、Aeacusでは必要になる。

0-RTTの扱い

既存接続の鍵を使って0-RTTデータを送る場合も、Initialと同じ5タプルなので同じ転送方法を適用できる。AeacusがDNS解決と転送を初期パケットに重ねることで、後述の負荷分散・サービス移行では「0-RTT接続開始」まで広げられる。

キャッシュ管理：接続状態をTTLの外側の根拠にする

1. QUIC monitorによる成否推論

QUICのペイロードは暗号化されているが、ヘッダのパケット種別は観測できる。Aeacusは短ヘッダの1-RTTパケットを観測するとハンドシェイク成功と推論する。反対に、タイムアウトまで1-RTTパケットが見えない場合は失敗とする。Initial内で復号できる CONNECTION_CLOSE があれば、タイムアウトより早く失敗を検知できる。

2. 期限切れだが最新のキャッシュを再生する

キャッシュを「存在しない / 有効 / 期限切れ」と保持し、さらに実際の権威DNSと比べて「最新 / 古い」と分類する。期限切れレコードを見つけると、Aeacusは古いレコード先へまずInitialを転送しつつ、並行してDNSを引き直す。

  • 古いレコードが実は最新だった場合：ハンドシェイクはそのまま成功する。DNS問い合わせ応答を待たない分、キャッシュヒット相当の低遅延になる。
  • 宛先サーバが応答しない場合：並列DNS解決の完了後、更新先へInitialを再送する。端末は応答を待っているため、接続機会は失われない。
  • 別サーバが応答するが認証に失敗する場合：monitorが失敗を検知し、古いエントリを削除する。端末のリトライは更新済みレコードで処理される。
  • 古いIPにも稼働サーバがいる場合：ロードバランサが割当先を変えたような場合で、TLS認証を通れば接続は継続する。並列DNSの結果でキャッシュは最終的に更新される。

3. サーバ起点に近い無効化

TTL中の有効キャッシュであっても、ハンドシェイク失敗は「IPが古い可能性」のシグナルである。Aeacusは該当エントリを削除し、DNSを再問い合わせする。実際にはサーバがDNSへプッシュ通知するのではなく、失敗した接続を観測することでサーバ変更の影響を検出する方式である。著者らはこれを server-triggered cache invalidation と説明している。

導入方法と互換性

UE側には軽量な Aeacus proxy を置く。ネットワーク接続直後にREST APIでAeacus対応ドメイン一覧を得る。対応ドメインにはDNSを実行せずAeacus resolverのIPを返し、非対応ドメインには通常DNS resolverとして振る舞う。5GからWi-Fiへ切り替わるなどLDNSが変われば、一覧を更新して通常DNSへフォールバックする。

「アプリケーション無変更」には境界がある。論文の主張は既存のDNSベースのアプリケーションコードを変更せず恩恵を受けられるという意味である。一方、実運用には5GC内のゲートウェイ/LDNSとの協調、UEのproxy、対応ドメインの管理、サーバ側の preferred_address 有効化が必要であり、インターネット全体に透過的に入る仕組みではない。

実装

環境実装・役割
5Gテストネットワーク3GPP Release 17準拠。UPFにRust製QUIC monitor（raw socket + pcap）、EASDFにRust製QUIC resolver、Pythonで拡張したLDNSを配置。UPF–EASDF間はGREトンネル、経路・送信元の調整にOpen vSwitchとNATを使う。
商用5Gネットワーク5GCを改変できないため、UDP proxy型の変形実装で評価。UEクライアントが全パケットをresolverへ送り、UDPペイロード先頭の4 byteに本来の宛先IPを付ける。MTU 1500 byteとQUICの1200 byte制約内に収まるようにした。
キャッシュ実装では小さいレコードをhash mapに無期限保持し、状態を管理。実運用ではメモリ制約に応じて古いレコードを退避することを想定する。

ユースケース：DNS負荷分散とサービス移行

DNSはCDNやエッジの負荷分散で、ドメイン名を「現在割り当てるサーバ」へ結び付ける用途にも使われる。著者らは2つの5GCと各エッジサーバを使い、UEが第1のネットワークから第2へ移る状況を評価した。権威DNSはEDNS0 Client Subnetを使って各LDNS近傍のエッジIPを返す。サーバ間ではTLSセッショントークンを安全に共有し、異なるサーバでもQUIC 0-RTTを可能にする。

方式移行後にHTTP応答を得るまで意味
Aeacus + トークン共有16.3 msresolverの処理・転送1.4 ms、RAN遅延10 ms、サーバ処理等を含む。DNS問い合わせなしで初期データを転送できる。
通常DNS26.3 ms移行先でUEのキャッシュがないためDNSが必要。
トークン共有なし47.5 ms0-RTTを利用できず、より長いハンドシェイクとなる。

これはAeacus単独の効果ではなく、DNS経路の短縮とQUIC 0-RTT、サーバ側トークン共有を組み合わせた実験である。実世界の無線・IP再設定時間はこの実験に完全には含まれず、論文自身も今後の課題としている。

比較対象・新規性

方式主な考え方Aeacusとの差
TTL調整 / ECO-DNSTTLを最適化してヒット率と更新性を折衷する。TTLに依存する限り、低遅延と更新のトレードオフを根本的には消せない。
DNScup権威DNSからLDNSへ更新をブロードキャストし、強い整合性を狙う。グローバルな配布はオーバーヘッド・展開性が課題。Aeacusは実際の接続失敗を局所的な更新契機にする。
DoH / DoQDNSの通信をHTTPS/QUIC上へ載せ、主にプライバシーを改善する。DNSとQUIC接続開始を同じ制御問題として結合するものではない。
QuicSocksDNS問い合わせとQUIC handshakeを結合して接続開始を速める。最も近い比較対象。Aeacusはさらに、接続結果に基づく期限切れキャッシュ再利用と能動的無効化を加える。
新規性を一文で言うと：DNSのTTLを直接賢くするのではなく、「QUICの接続が通ったか」という下位層の観測をDNSキャッシュの有効性へフィードバックし、さらにDNS待ちをQUICの最初のパケット転送に畳み込んだクロスレイヤ設計である。

批判的に読むべき点・限界

  1. 適用範囲はQUICかつ協調可能な5G環境に限られる。5GCのゲートウェイとLDNSを制御し、UEをカスタマイズできることが前提である。論文も一般ネットワークへの展開は将来課題としている。
  2. サーバ側の要件がある。preferred_address を必要とするため、QUICサーバがこの機能を有効にしていない場合は、そのままAeacus対応にはならない。
  3. キャッシュ不整合の検知は「接続失敗後」である。障害を予知する方式ではなく、失敗またはタイムアウトを契機に更新する。応答がないと最大約3秒待つ評価設定であり、完全に無停止ではない。
  4. 古いIPでも接続が通ることを許容する。負荷分散で旧サーバが生きていれば可用性には有利だが、常に最新のDNS割当先へ厳密に行くこととは異なる。論文はこれを許容可能なケースとして扱う。
  5. 商用網の評価は変形実装である。商用5GCを改変できないためUDP proxyを使った評価であり、完全な5GC内実装はテストネットワークで検証している。商用大規模展開時の運用・障害分離・プライバシーの評価は限定的である。
  6. セキュリティ上の前提を要確認。論文はTLS証明書検証、QUIC接続ID、限定された再転送を根拠に中間者・増幅攻撃への耐性を論じる。一方でresolverがInitialを復号しSNIを扱うため、事業者コア内へ可視性と信頼を置く設計であり、ECH等との将来の相互作用は本論文では深く評価されていない。

卒論テーマ（MQTT / QUIC / V2X）との接点

この論文はMQTT-over-QUICのデータ転送性能を測るものではない。しかし、QUICをトランスポートとして採用すると、接続確立・再接続・移動時の名前解決がエンドツーエンド遅延の一部になることを具体的に示す。移動体やエッジサービスを扱う研究では、アプリケーションメッセージの遅延だけでなく、接続開始・再接続・サービス移行を別の評価軸として置く根拠になる。

  • 使える観点：キャッシュTTL、DNSミス、ハンドシェイク回数、モビリティ時の再接続時間を分けて測る。
  • そのまま移せない点：AeacusのDNS+QUIC結合は5GC側の経路制御とクライアントproxyを必要とする。MQTT brokerへQUICを載せるだけでは実現しない。
  • 実験案：V2CシミュレータでDNSキャッシュヒット/ミス、接続再開あり/なし、MQTTのTCP/QUICを分け、制御メッセージの定常時遅延と「接続から最初の制御成功まで」を別指標にする。
