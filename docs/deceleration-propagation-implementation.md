# 減速伝播を用いた交渉判断の実装指示書

実装担当者への依頼。`mcs-tiv`の`fix/reproduction-paper`を基点とする独立した作業環境で、既存の走行ロジックを利用した減速伝播予測と、承諾時・拒否時の累積損失比較を実装する。別の環境で進行中の論文再現実験は、完走を待たずにそのまま継続させる。

新しい走行制御器を作ることが目的ではない。山下さんのTIVで行っている「交渉を承諾するかどうかの評価」を、今から10秒間の減速・回復と後続車への影響に基づく評価へ発展させる。

## ユーザーと合意した方針

- MCSの軌道交換、衝突確認、交渉、合意後の軌道切り替えという枠組みを維持する。
- 速度の生成・選択・指示には既存の実装を再利用する。最速候補を選ぶ独自制御や、別の追従モデルへの置き換えは行わない。
- 評価対象は10秒後の速度だけではなく、現在から10秒後までの速度変化とする。
- 損失の意味は「この交渉相手との干渉がなければ走れた速度に対して、どれくらい走れなくなったか」。途中の減速、その継続時間、回復過程を含める。
- 承諾時と拒否時の両方について、要求車・受入判断車・双方の後続車列を評価し、総損失を比較する。
- 拒否した場合、その交渉によって双方の元の`planned`を変更しない。拒否を、逆向きの交渉成立や相手への強制的な譲歩指示に読み替えない。
- 予測誤差は既存手法にも存在し得る。今回の予測が実走行と一致することや、既存実装だけで精度が十分であることは未検証である。

この会話の方針は、以前の説明資料やメモより優先する。特に「拒否時は受入判断車のdesiredと要求車の新しい譲歩軌道を採用する」という古い説明は採用しない。

2. 再現実験が参照するチェックアウトでは、ブランチ切り替え・コード編集・生成入力の変更を行わない。既存の実験プロセスを停止しない。
3. `fix/reproduction-paper`の採用コミットから、独立したworktreeまたは作業コピーと新規ブランチを用意する。新規名の案は`codex/deceleration-propagation`。同名作業が存在すれば内容を確認し、上書きしない。Codexの管理worktreeツールが利用できる場合はそれを優先する。
4. 元ブランチへのマージ、force push、実験条件の更新はこの実装に含めない。元の未コミット変更も勝手に移動・破棄しない。
5. 検証出力は毎回新規ディレクトリへ保存する。論文再現のCSV・ログ・生成XMLへ混在させない。再現中のマシンで重い実験を並走させず、短い確認から始める。

## 既存コードと追加する処理の境界

MCSはManeuver Coordination Service、TIVはTrajectory Influence Valueを指す。READMEに異なる展開表記が残っていても、設計上の意味はこの定義に合わせる。

山下さんのTIVは、共有軌道の終端速度と距離係数`R(X)`などを評価に使う。今回の予測は、既存の受信軌道の全速度サンプルを足すだけではない。交渉結果が変わったときの後続車の応答を、既存の走行ロジックで計算する必要がある。

| 役割 | 確認する主なコード |
| --- | --- |
| 現在のTIV計算、送信側評価、受信側判断 | `func/thesis_tiv.py`の`score`、`environmental_term`、`send_mcm`、`judge_yield` |
| 状態更新、再計画、代替軌道生成、候補選択、速度指示 | `func/cav_three_junction.py`と`func/cav_three_junction_bus.py`の`updateStatus`、`updatePlannedPath`、`generatePlannedPath`、`generateAlterPath`、`selectBestPath`、`executionDrive` |
| 軌道候補生成、車種別制約、補間、緊急停止 | `PathPlanning/FrenetOptimalTrajectory/frenet_three_junction.py` |
| SUMO更新、前ステップのMCM受信、制御、次ステップへの送信 | `junction/junction_three_agree.py` |
| 既存仕様の回帰テスト | `tests/test_thesis_tiv.py`、`tests/test_thesis_conditions.py` |
| 再現上の前提と評価条件 | `docs/thesis-audit.md`、`docs/yamashita-evaluations.md`、`thesis_evaluations.py` |

初期実装はT字路で検証する構成を推奨する。CarとBusの性能差を扱える共通設計にし、十字路・合流への接続は段階を分ける。T字路だけの検証を全シナリオ対応と報告しない。

## 承諾時と拒否時の定義

要求車をA、受入判断車をBとする。予測開始状態をコピーし、同じ初期状態から2ケースを計算する。

| ケース | 要求車Aの起点軌道 | 受入判断車Bの起点軌道 | 後続車 |
| --- | --- | --- | --- |
| 承諾 | 対象の`desired` | 対象の`desired`に譲るために生成・選択した`alternative` | それぞれ変更後の先行車に対する応答を予測 |
| 拒否 | 交渉直前の`planned` | 交渉直前の`planned` | それぞれ元の先行車計画に対する応答を予測 |

これは交渉結果による起点の違いであり、10秒間ずっと再計画しないという指定ではない。予測中も既存の更新条件を反映する。ただし未来の新たな交渉を再帰的に解き続けたり、予測器から予測器を呼ぶ処理にはしない。評価中の交渉結果は与えられた条件として扱い、それ以外の未来の交渉・未知の流入については予測範囲外として記録する。

合意フェーズが有効なら、承諾判断と軌道の実行開始は同時とは限らない。既存の合意待ち・有効期限・切り替え条件を壊さず、予測で置いた実行開始時刻を明示する。

実行可能な代替軌道を作れなければ、損失が小さそうでも承諾しない。元の物理的な可否判定を先に行う。

## 損失の基準と計算

### 基準速度の意味

各車両の基準速度列は、当該交渉相手との競合・譲歩制約だけを外した場合の走り方を表す。最高速度を一律に当てはめたり、全車両を消した自由走行を基準にしたりしない。初期位置・速度、車種性能、道路・旋回制約、関係のない先行車や障害物は保つ。

後続車については、直前の車を単に消すのではなく、当該交渉による減速がなかった場合の先行車の動きに追従する基準を考える。要求車に`desired`があるからといって、全後続車にも適切な`desired`が存在すると仮定しない。

各車両の基準速度列、評価対象車両集合、時間区間は、承諾・拒否で共通にする。既存軌道を基準として流用する場合は、この意味に合うことを確認する。初期状態がすでに過去の譲歩の影響を受けていても、過去へさかのぼって位置や速度を作り直さない。

### 初期検証用の計算案

以下は実装を進めるための提案であり、正規化や元のTIVとの合成までユーザーが確定したものではない。まず設定可能な形で実装し、実際の判断に使う前に下記の設計確認を行う。

- 予測時間は10秒、刻みは既存シミュレータに合わせて0.1秒とする。
- 車両ごとに「基準速度 − ケースの予測速度」を時間方向に積み重ね、それを対象車両全体で合計する。
- 基本形は`L_case = Σ_i Σ_k (v_ref[i,k] - v_case[i,k]) × dt`。0.1秒の100区間を積算し、101個の状態サンプルすべてに重複して重みを付けない。区間速度の定義と積分方法は両ケースで統一する。
- この形の単位はmであり、速度低下による累積の進行距離損失を表す。遅延秒数や衝突確率と呼ばない。速度差だけを足して`dt`を省かない。
- 比較値は`L_reject - L_accept`。正なら承諾側の予測損失が小さい。負なら拒否側が小さい。
- 実質的に負の車両損失が出た場合、利益として扱ったり、無条件に`max(0, ...)`で隠したりしない。該当速度列と基準を記録し、基準の構成・制約・時間合わせを確認する。微小な数値誤差用の許容値は、物理的な負の値と区別する。

共通の基準・対象・窓なら、符号付き差分の比較では基準項が相殺される。この性質をテストに使えるが、基準の構築と車両ごとの損失説明を省略する理由にはしない。ケースごとのクリッピングや正規化でこの性質は変わる。

### 実判断への接続前に確認する選択

1. 基準速度列を既存のどの処理・入力から作るか。「相手の影響だけを外す」の具体的な対象を、A・B・各後続車について短く提示する。
2. 距離損失の非正規化和でよいか、別の正規化が必要か。上記の単位と選択結果への影響を説明する。
3. 元のTIVの到達時間項・性能項をどう扱うか。今回の議論だけで削除または存続が確定したものにしない。異なる単位の新しい損失へ元の重み`-0.1`等をそのまま流用しない。車両性能を予測に反映することと、別の性能優先項を残すことは別の判断である。
4. 同損失・僅差時の扱い。初期案は既存TIVへフォールバックするが、数値許容値とともに明示する。

これらの確認待ちでも、予測器、損失計算、ログ、テスト、判断を変えない比較モードの実装は進められる。未確定の研究上の選択を黙って固定し、完成扱いにしない。

## 既存走行ロジックを予測に再利用する方法

既存の軌道生成器だけで、承諾・拒否ごとの車列予測が完成しているわけではない。必要な追加は、コピーした状態で既存処理を繰り返す予測用の組み立てである。

1. 実車状態・受信MCM・対象軌道・車種制約を読み取り、変更不能なスナップショットを作る。
2. 承諾・拒否・基準の状態をそれぞれ分離する。先行車の計画変更を後続車が受け取り、再計画する順序を再現する。
3. 既存の候補生成、衝突・性能チェック、コストによる候補選択を使う。最高速度の候補を独自に選び直さない。
4. 予測速度は単に`path.s_d`を読むだけにせず、`executionDrive`の位置差からの速度計算と車種別の加減速制限まで合わせる。
5. 実状態を更新する処理と計算部分を分離し、予測中に`traci.vehicle.setSpeed`、経路変更、`simulationStep`などを実環境へ発行しない。必要ならTraCI依存を読み取り専用入力や予測用アダプタへ置き換える。
6. 実車の軌道、`pathID`、合意待ち状態、サーバー、カウンタ、乱数状態を予測で変更しない。単なる浅いコピーでは不十分な箇所をテストする。

現在の`updateStatus`には、SUMOから取得した位置を予定軌道上の位置で置き換える処理がある。予測との一致を議論するときは、「SUMOの実測状態」と「制御内部の状態」を区別する。この研究実装のついでに既存の状態定義を変更しない。

時間刻み0.1秒と、候補軌道の再生成期限1秒を混同しない。既存の先行車変化・無効化による期限前の再計画も保持する。速度列を記録するためだけに、Frenet候補を毎0.1秒で無条件に全生成する実装にしない。

10秒先までの経路が不足する場合は、既存ロジックによる再計画や補間を明示的に扱う。送信軌道は受信時点で残り10秒未満の場合がある。終端等速などを使った区間は仮定としてタグ付けし、欠損を速度ゼロや損失ゼロで埋めない。両ケースの比較窓は一致させる。

## 後続車と利用できる情報

地図で定義済みの道路ID・車線ID・車線番号・車線内進行位置を車両状態に保持し、送信する
MCM軌道にも現在値を載せる。座標から車線を推定しない。同じ車線IDの車両は、
曲線上でも有効な車線内進行位置で前後を判定する。車線IDが異なる場合でも、将来軌道が同じ
下流回廊へ収束し、かつ向きがそろう車両は合流後の後続候補とする。直交する
交差軌道は後続車へ混ぜない。古いMCMに車線情報がない場合だけ、従来の幾何
判定へフォールバックして互換性を保つ。

MCMのyawは停止時の向きと、異なる車線が同じ向きで収束するかの確認に使う。
同一車線の前後順序を現在yawへの直線投影だけで決めない。0.1秒後との位置差だけで
向きを再計算してはならない。yawが欠けた旧ログでは、軌道上の前後にある最初の
非ゼロ変位を探し、それも存在しない場合だけ評価不能とする。

- A・B自身を含め、双方の後続車の集合を取る。同じ車両IDを二重加算しない。
- 片側のケースだけ対象車を減らすなど、比較を有利にする対象選択を行わない。
- 後続車への影響を逐次予測する場合、従来の`R(X)`を根拠なくさらに掛けて二重に減衰させない。
- 通信範囲と影響の到達範囲は別である。受信できた最遠の車より先に車がいないとは仮定しない。観測車両の範囲での損失として報告する。
- 車列の重なり、同時に複数の交渉がある場合、単純な独立2車列では扱えない。最初は検出して既存判定へ戻し、対応率と理由を記録する。個々の1対1で有利だった結果を、そのまま多対多の最適解とみなさない。

オンラインの判断入力は、自車・取得可能なセンサー情報・受信MCMの範囲に限定する。未来のSUMO状態や、通信外の全車両オブジェクトを参照して性能を良く見せない。検証用の実測ログは利用できるが、オンライン予測の入力へ逆流させない。

MCMへスコアを載せる案を優先する。例えばAが自分側車列の承諾・拒否損失を計算し、Bが自分側の損失と合わせる方式が考えられる。ただし追加フィールドと計算分担は設計案として提示し、既存通信で全必要情報が自動的に揃うと扱わない。

追加情報には、対象の要求・受入車ID、軌道ID、生成時刻、評価窓、手法の版、対象車両ID、計算の有効性を対応づける。古い軌道に対するスコアを新しい交渉へ適用しない。送信側と受信側で窓がずれる場合、単一の合計値だけでは補正できないため、共通窓の決め方または区間別情報を設計する。既存の1ステップ通信遅延を無視しない。

## 段階的な実装

以下のモード名・新規ファイル名は案であり、既存の構造に合わせて整理してよい。既存の`MCS_TIV_IMPLEMENTATION`や方式番号を黙って再定義しない。

### 第1段階 共通部と比較モード

- 既存テストを実行して基点の結果を記録する。
- 予測用スナップショット、既存走行ロジックのアダプタ、車列予測、損失集計を分離する。例えば`func/deceleration_prediction.py`と`func/deceleration_loss.py`を新設する。
- 新機能はデフォルトOFFにする。`shadow`相当の比較モードでは、実際の交渉判断は元のTIVに任せ、新手法の予測だけを記録する。
- OFF時の挙動を維持し、比較モードでも同一入力・seedの軌道、指示速度、交渉結果が変わらないことを確認する。実時間の増加は別途測る。
- 前述の未確定な研究上の選択を、最小の提案とテスト例を添えてユーザーに確認する。

### 第2段階 実判断への接続

- 確認済みの損失定義と選択規則を`active`相当の明示的モードで接続する。
- 承諾の根拠だけを変更し、物理的な可否判定、合意フェーズ、有効期限、軌道切り替えを維持する。
- 予測不能、必要情報不足、古いスコア、対象外の複数交渉などでは、既存の可否確認を通した元のTIV判定へ戻し、理由を数える。計算失敗をゼロ損失や承諾に変換しない。
- 本実験では新手法が実際に使われた割合とフォールバック率を必ず併記する。ほぼ全件フォールバックの結果を新手法の性能と報告しない。

### 第3段階 検証と実験

- 人工的な単一車列で、先行車の減速・後続への波及・回復を確認する。
- T字路で短い比較を実行し、実際に交渉と予測が発生したことをカウンタで確かめる。空の試運転を検証成功にしない。
- Carのみ、CarとBus混在を順に確認する。
- 長時間・複数seed実験は、短区間で計算時間と動作を確認した後に行う。進行中の再現実験とCPU・メモリ・出力先を競合させない。

全車両・全候補の10秒先までのSUMO複製実行を、交渉ごとに起動する設計にはしない。局所的な予測を優先し、同一スナップショット・軌道ID・制約での再利用を検討する。キャッシュする場合は、状態・時刻・車列・シナリオの変更による無効化をテストする。計算量をFrenet候補生成コスト込みで測り、根拠なく`O(NK)`だけで軽いと判断しない。

## テストと記録

少なくとも以下を自動テストまたは再実行可能な短い検証で確認する。

1. 相手による影響がないケースでは基準との差が数値許容内でゼロになる。
2. 10秒後の速度が同じでも、途中の減速が長いケースの損失が大きくなる。
3. 既知の速度差の積分値と一致し、`dt`、区間数、単位が正しい。
4. 拒否時に双方の元の`planned`が保たれ、勝手な逆向き譲歩を作らない。
5. 同じ境界入力では既存の候補選択・速度指示と予測用アダプタの結果が一致する。
6. CarとBusの速度・加減速制約を正しく区別する。
7. 先行車の変更が、実装の受信・更新順に沿って後続へ伝わる。10秒以内に影響を受けない車まで強制的に減速させない。
8. スナップショットの独立性、乱数状態の不変性、予測中に実環境への更新命令が出ないことを確認する。
9. 車両IDの重複、隣車線・交差方向、車列の重なりを扱う。
10. 古いMCM、軌道ID不一致、短い軌道、欠損、到達不能、候補なしで、不正なゼロ損失・無条件承諾が発生しない。
11. 同損失・数値許容・負の損失・評価時刻の不一致をテストする。
12. OFFと比較モードで元の走行が変わらず、既存テストが維持される。

予測誤差は、予測時点で速度列を保存し、その後にSUMOから取得した実速度と同じ車両ID・絶対時刻で比較する。少なくとも予測先1秒・5秒・10秒の誤差、窓全体の平均絶対誤差、最大誤差、対応サンプル数を記録する。途中で退出した車両を速度ゼロとして数えない。新たな交渉や再計画が起きたケースを分類できるようにする。

実走行と直接比較できるのは、実際に選ばれたシナリオだけである。基準速度そのものは反実仮想なので、予測した共通基準を固定して実速度を代入した損失と比較する場合、その条件付き評価であることを明記する。選ばれなかったケースや基準の正しさまで検証するには、同一状態からの別のオフライン比較が必要であり、通常の1回の走行ログで検証したことにしない。

判断ログには、ケースID、時刻、車両・軌道ID、対象集合、基準・承諾・拒否の速度列、車両別・側別の損失、最終判断、元のTIV判断、予測時間、補間等の仮定、フォールバック理由を対応づける。大量ログはサンプル保存等で制御し、性能計測と分ける。

実験結果には平均速度等の交通効率に加えて、実際のSUMO衝突情報、緊急制動、性能制約違反を記録する。既存の衝突カウンタがゼロなだけで安全確認済みとしない。既存の`emergency_stop`返却後に衝突を再検査しない経路も、再利用しただけで安全保証が得られるわけではない。既存の問題を見つけた場合は、新手法の性能改善と混ぜず、独立した修正として報告する。

## 実行方法と引き渡し条件

既存の単体テストは、対象PCで使うPython環境を確認してリポジトリルートで実行する。

```sh
python3 -m unittest discover -s tests -v
```

短い実行は、入力生成用の`--duration 600`を保持し、対応ランナーの`--stop-time`で停止する。`--duration`を短くすると、流入スケジュールや車種抽選まで変わり得る。`--no-save`だけでは生成ファイルの共有を防げないため、独立作業環境と出力先も必要である。

`scripts/run_thesis_case.py`は隔離実行の参考になるが、現状は`MCS_TIV_IMPLEMENTATION=thesis`を明示し、このMac固有の論文パスも参照する。そのまま別PCの新手法ランナーとして使わず、設定可能な専用ランナー等を用意する。SUMO・TraCI・Python・依存ライブラリの版、入力ファイルのハッシュ、seedの型と値、車種割当方式を記録する。

引き渡しでは次を報告する。

- 作業ブランチ、基点SHA、変更コミットと変更ファイル。
- 再利用した既存処理と、新しく実装した予測・評価部分。
- 確認済みの損失定義、残る設計判断、未対応シナリオ。
- OFF・比較・実判断の切り替え方と、他PCでも再実行できるコマンド。
- 既存テスト・追加テスト・短い実走行検証の結果と出力先。
- 誤差、計算時間、新手法の適用率、フォールバック率、安全関連の観測結果。
- 進行中の再現実験とその入力・結果を変更していないこと。

まずは独立環境の準備、基点テスト、既存処理の切り出し、比較モードまで進める。研究上の選択が必要な部分だけを具体的に確認し、判断が確定したら実判断への接続まで進める。再現実験の完走は実装開始の前提にしない。
